GOVERNANCE PRINCIPLES

所有管理決策都應回答四個問題

人

誰

是個人、群組、角色，還是系統整合身分？

域

能碰什麼

圖面、資料來源、資料夾或管理能力的範圍為何？

權

可以做什麼

只能瀏覽、可編輯、可管理，或具有最高管理責任？

證

如何證明

誰核准、何時生效、如何驗證、能否追溯與回復？

授權不是一次性設定；人員、任務與資料範圍改變時，權限也必須跟著被重新檢視。

OPERATING CYCLE

治理工作形成持續循環

1申請目的、範圍與期限
2審核責任人與風險
3配置身分、群組與權限
4驗證以實際角色測試
5監看狀態、稽核與異常
6回收調職、到期與離職
管理完成的定義：設定已儲存、實際角色已驗證、變更已有紀錄，而且到期或不再需要時有明確回收方式。
IDENTITY MODEL

使用者、群組與角色各自解決不同問題

👤

使用者 User

回答「這個人是誰」，記錄帳號、狀態與最後登入。

＋
👥

群組 Group

回答「這群人共同負責什麼範圍」，適合授予資源權限。

＋
◆

角色 Role

回答「可執行哪類平台職責」，避免逐人堆疊能力。

個人例外權限應有原因與期限；長期共通需求應整理為群組或角色。

USER LIFECYCLE

帳號從建立開始，就要規劃最後如何回收

01

建立

確認真實人員、顯示名稱、聯絡資訊與責任單位。

02

授權

依工作內容加入群組與角色，避免直接給予過高權限。

03

驗證

以該帳號確認可見圖面、可讀資料與可用功能。

04

定期檢視

檢查最後登入、異常使用與長期未用帳號。

05

異動或離職

先停用、回收群組與角色，再依規範處理保留。

不要共用帳號：共用身分會讓稽核無法指出真正操作者，也讓離職或密碼外洩後難以精準回收。
GROUP DESIGN

群組以「責任範圍」設計，比以人名設計更穩定

依組織

例如廠區、產線、班別或部門，適合穩定的責任邊界。

依任務

例如能源監看、品質分析或專案建置，適合跨單位合作。

依期間

例如承攬商或臨時專案，必須設定到期與定期檢視。

名稱看得出範圍與用途。
說明記錄擁有者與適用規則。
成員只保留仍有業務需要的人員。

停用群組後，其成員不再取得該群組授予的權限；停用前仍須盤點實際影響。

ROLE DESIGN

角色描述平台職責，群組描述資源範圍

角色適合管理

  • 一般監看、Studio 設計、系統管理等職責
  • 跨多個資源但能力一致的工作模式
  • 需要由治理規則統一控管的管理能力

群組適合管理

  • 特定廠區、產線、專案或資料範圍
  • 會隨組織與任務調整的成員集合
  • 同一批人共同需要的資源授權
設計口訣先決定「負責什麼」的群組，再決定「能做什麼」的角色，最後才處理必要的個人例外。
PERMISSION MODEL

一筆權限由資源、授權對象與操作層級組成

ResourceDataSource／Display／Folder
＋
PrincipalUser／Role
＋
Access LevelRead／Write／Manage／Administrator
判讀順序：先確認資源種類，再確認授權給誰，最後確認允許的操作層級；不要只看到「有權限」就判定設定正確。
TWO-LAYER AUTHORIZATION

看得到圖面，不代表讀得到圖面上的資料

▣

圖面權限

控制 Display 或 Folder 的可見、編輯與管理範圍。

回答：能否開啟與維護畫面？
＋
⌁

資料權限

控制 DataSource 的讀取或設定能力，以及下游資料是否可取得。

回答：畫面能否取得資料？
＝
✓

完整使用

同時具備圖面與必要資料權限，Runtime 才能正確呈現。

有圖、無資料

Display 可開啟，但數值空白或查詢被拒絕。

有資料、無圖

具備來源讀取能力，但無法瀏覽指定 Display。

兩者都有

在授權時間與範圍內完成監看或分析。

ACCESS LEVELS

不同資源支援的權限層級不同

DataSourceRead：讀取必要資料。
Write：維護來源設定。
DisplayRead：瀏覽。
Write：編輯。
Manage：管理圖面與其治理事項。
FolderRead：瀏覽。
Write：編輯內容。
Manage：管理結構。
Administrator：最高治理責任。

權限層級越高，代表的不只是能做更多操作，也代表更高的變更與誤用風險。

EFFECTIVE PERMISSION

使用者的最終能力，可能來自多條授權路徑

直接授權User → Resource
角色授權User → Role → Resource
擁有者或管理責任Owner／Administrator
有效結果合併後的實際可用層級

排查時要問

  • 使用者帳號與所屬群組是否啟用？
  • 角色是否仍符合目前職責？
  • 權限是直接授予還是由角色取得？
  • 資源是否位於另一個 Folder 範圍？
  • 是否誤把管理員測試結果當成一般使用者結果？
PERMISSION VERIFICATION

權限驗證必須使用代表性帳號與實際操作路徑

1準備測試帳號一般監看或設計角色
2檢查導覽只看得到允許的範圍
3開啟 Display圖面權限正確
4驗證資料即時與歷史均可讀
5測試禁止項目不應使用的能力確實被擋下
驗證不是只測成功：還要證明使用者看不到不屬於自己的圖面、資料與管理功能。
LOCALIZATION GOVERNANCE

多語系是受控內容資產，不只是介面翻譯

System

平台固定文字，需保持術語一致與升級後可追蹤。

Public Dictionary

跨多個 Display 共用的名稱與現場詞彙。

Display Dictionary

只屬於特定 Display 的情境文字與顯示內容。

01

篩選範圍

確認語系、內容類型與 Display，避免修改錯誤範圍。

02

維護來源與譯文

保留 Key 與變數占位符，不任意改變格式。

03

驗證與預覽

檢查缺漏、重複、長度、單位與實際畫面結果。

04

批次變更

先驗證批次內容，再由負責人保存並抽查。

CACHE OPERATIONS

Cache 是 Runtime 查詢的承載與分流層

資料來源
正式資料仍由來源系統負責
→
Cache
保存可重用的查詢結果
Runtime ARuntime BRuntime C
  • 相同或相近查詢可重用結果，降低來源端重複負荷。
  • 多個 Cache 節點可以承接不同工作量，形成負荷分流。
  • Cache 不取代 DataSource，也不能掩蓋來源停止更新的問題。
  • 清除 Cache 會增加短期回源查詢，操作前必須評估影響。

多台 Cache 的價值，是把查詢負荷分散到適合的節點

DataSource
管理重點：節點要有可辨識名稱、啟用狀態、連線驗證與清楚用途；不能只看「有幾台」，還要確認實際查詢是否被正確分流。
CACHE HEALTH

用四組訊號判斷 Cache 是健康、吃緊或失去服務

連線與節點

健康狀態、節點角色、版本與連線延遲。

記憶體

已使用容量、限制與淘汰策略是否合理。

命中與操作

命中率、每秒操作量與 Runtime key 數量。

資料生命週期

永久、即將到期、歷史或孤兒資料的比例。

判讀原則單一數字沒有絕對好壞；要與平日基準、使用人數、查詢類型及異常時間一起比較。
TTL & SAFE CLEANUP

先控制生命週期，再考慮刪除 Cache

01

確認範圍

辨識近期、歷史、永久、孤兒或特定 DataBinding key。

02

評估影響

確認清理後哪些 Runtime 會重新向來源查詢，以及來源能否承受。

03

優先套用 TTL

透過到期策略逐步回收，避免一次清除造成尖峰。

04

最小範圍處理

只處理已確認的 key 或節點，不把全清當成標準排障步驟。

05

處理後觀察

追蹤命中率、記憶體、來源負荷與 Runtime 回應。

高風險動作：清除全部 Runtime Cache、移除節點或大幅縮短 TTL，應先有核准、維護窗口與回復方案。
AUDIT TRAIL

稽核紀錄用來重建「誰在何時做了什麼，結果如何」

時間與使用者操作發生時間、使用者識別與 Client IP。
事件與資源Event Type、Resource Type、模式與查詢摘要。
結果與效能成功／失敗、錯誤代碼、耗時與資料列數。

適合回答

異常前後發生過哪些操作？特定變更是否成功？問題影響哪些資源？

不應取代

事件處理紀錄、變更單與業務原因仍要由負責人補充，不能只留下技術事件。

分享稽核畫面前，應遮蔽不必要的帳號、IP、查詢內容及其他敏感資訊。

BACKUP & RESTORE

備份成功只是第一步；可解密、可驗證、可還原才算可用

完整備份

適合重大變更、升級前與定期保護，涵蓋平台主要設定與資產。

快速設定備份

適合日常設定保護與較快的管理作業。

自訂資料備份

依需求選擇身分、設定、Cache、語系、資料來源、Display、媒體或稽核等範圍。

1建立選模式、範圍與加密密碼
2保存分離正式環境與備份位置
3檢查檔案有效、清單與版本可讀
4演練在受控環境執行還原
5驗證登入、權限、資料與 Runtime
RESTORE DECISION

還原是平台變更，不是單純把檔案放回去

還原前

  • 確認備份來源、建立時間與有效狀態
  • 確認完整或部分還原範圍
  • 選擇覆寫或只插入新資料的衝突策略
  • 通知受影響人員並安排維護窗口
  • 保留還原前自動或人工完整備份

還原後

  • 確認使用者、角色、群組與權限
  • 驗證 DataSource、View 與 DataBinding
  • 抽查 Display、媒體與多語系內容
  • 確認 Cache 與 Runtime 查詢恢復
  • 記錄結果、差異與後續處理
加密密碼遺失：備份可能無法還原；密碼必須由受控方式保存，且不可與備份檔放在同一個不受保護的位置。
CHANGE & INCIDENT LOOP

從發現問題到關閉事件，每一步都要留下可驗證結果

1發現使用者回報或狀態告警
2分級影響、急迫與範圍
3止血最小範圍降低影響
4修復依核准方案執行
5驗證技術與使用者雙重確認
6結案原因、紀錄與預防措施
權限異常先確認帳號、群組、角色與兩層權限。
資料異常沿 Display → Binding → View → DataSource 排查。
效能異常比較 Runtime、Cache 與來源端狀態。
OPERATIONS CHECKLIST

把治理轉成固定節奏，避免只在故障時才管理

每日／值班

  • 平台與 Cache 健康狀態
  • 重大失敗與異常稽核事件
  • Runtime 使用者回報

每週／每月

  • 未使用帳號與權限例外
  • Cache 容量、命中與 TTL 趨勢
  • 備份結果與容量

重大變更前後

  • 影響盤點與完整備份
  • 維護窗口與回復方案
  • 端到端驗證與稽核紀錄

巡檢紀錄應能看出：檢查時間、檢查者、判斷依據、異常內容、處理人與完成狀態。
