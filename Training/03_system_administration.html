安全原則
連線帳號不得與個人帳號混用；憑證、密碼與端點資訊只提供給必要的管理角色，並依組織規範定期檢視。
VIEW & DATA MODEL

把來源資料整理成設計者看得懂、用得對的結構

  • 名稱應能辨識設備、區域與用途
  • 欄位應標示資料型別與單位
  • 時間欄位與更新頻率需有明確定義
  • 避免讓設計人員直接猜測原始代碼
  • 結構異動前先盤點受影響的 Display

TWO-LAYER PERMISSION

授權要同時回答：「能進哪裡」與「能看什麼」

▧

圖面權限

控制 Display 的瀏覽、設計或管理範圍。

  • 依工作情境分配
  • 避免用單一畫面繞過角色界線
  • 異動時確認導覽與入口
⌁

資料權限

控制資料來源、View、Tag 或相關內容的使用範圍。

  • 依資料責任與敏感度分配
  • 確保 Studio 與 Runtime 結果一致
  • 驗證拒絕存取時的安全呈現

權限驗證必須使用實際角色帳號；管理員本身看得到，不代表一般使用者也能正確使用。

LOCALIZATION

讓相同畫面以一致術語服務不同語系使用者

  • 先定義組織共用的產品與設備術語
  • 使用穩定的文字識別，不以顯示文字當代碼
  • 新增語系時確認長文字與版面空間
  • 更新後抽查 Studio 與 Runtime 實際呈現
管理重點
翻譯正確之外，也要確保不同畫面對同一事物使用相同名稱。

CACHE OPERATIONS

管理操作前，先判斷影響範圍與恢復方式

01

查看狀態

確認節點可用性、容量、負荷與資料更新情形。

02

辨識範圍

確認問題屬於單一資料、來源、節點或整體服務。

03

選擇性處理

優先採用影響最小的更新或清除範圍。

04

持續驗證

確認 Runtime 資料恢復、負荷穩定並記錄結果。

注意
全面清除可能造成短時間重新載入與來源負荷上升，不應把它當作所有問題的第一個處理步驟。
SYSTEM HEALTH

從服務、資料與使用情境三個層次判斷健康狀態

平台服務

服務是否可用、回應是否正常、各節點是否一致。

資料管線

來源連線、更新時間、錯誤與 Cache 狀態是否正常。

使用者情境

特定角色、Display、時間查詢或裝置是否受到影響。

先界定影響範圍，再找共同原因：一個人、單一畫面、單一資料來源，還是整體服務？

BACKUP & RECOVERY

備份的價值，要用「能否成功回復」來驗證

1定義範圍設定、圖面與必要資料
2安排週期依重要性與變更頻率
3保護備份權限、位置與保留期限
4定期測試於受控環境演練回復
5記錄結果時間、版本與驗證項目
最低要求管理團隊知道備份在哪裡、由誰負責、多久執行一次，以及最近一次回復測試何時成功。
AUDIT & TRACEABILITY

留下足以還原事件的紀錄，不只寫「系統異常」

何時發生時間與持續期間
何人使用者、角色或執行者
何處環境、Display、資料來源
何事症狀、訊息與影響範圍
做了什麼操作步驟與變更內容
結果恢復時間與後續追蹤

記錄中避免直接暴露密碼、憑證或不必要的敏感資料。

CHANGE MANAGEMENT SOP

每一次正式變更都應有完整閉環

1提出目的與需求
2評估影響與風險
3備妥備份與回復
4執行限定範圍操作
5驗證資料與使用情境
6記錄結果與交接

技術驗證

服務、資料連線、Cache 與錯誤狀態正常。

使用驗證

以實際角色進入 Runtime，確認 Display 與資料均可用。

ADMIN ASSESSMENT

第三階段實作任務

任務 1

建立測試資料來源，完成連線與欄位驗證。

任務 2

建立測試群組，分別設定圖面與資料權限並以角色帳號驗證。

任務 3

說明 Cache 節點狀態，示範如何判斷影響範圍與選擇處理方式。

任務 4

依標準格式完成一次模擬異常的處理與變更紀錄。

完成標準能獨立執行低風險日常管理，並在高影響操作前完成評估、備份、驗證與紀錄。
